做 3D 建模的人都知道，从零开始创建一个精确的三维模型有多痛苦——要么得精通 Blender 这类专业软件，要么得花大价钱请建模师。但如果我告诉你，现在只需要一张图片，就能自动生成可编辑的 Three.js 代码呢？

今天的文章，我们来认识一个开源项目：**img2threejs**——一个能将普通图片转换为程序化 Three.js 模型的工具。按老规矩，由浅入深：先讲清楚为什么图片转 3D 这么难（理论），再带你跑通完整流程（实践），最后扒一扒它的核心原理（深入），附一份避坑清单。

## 第一章：为什么图片转 3D 这么难？

### 传统 3D 建模的痛点

在理解 img2threejs 之前，我们先看看传统 3D 建模面临哪些挑战：

```text
1. 高门槛 —— 需要掌握 Blender、Maya 等专业软件，学习曲线陡峭
2. 耗时耗力 —— 一个精细模型可能需要数小时甚至数天
3. 非结构化 —— 导出的通常是网格数据（mesh），难以编辑和动画
4. 缺乏语义 —— 模型是一堆顶点和面片，不知道「这是门把手」「那是铰链」
```

### 为什么需要「代码化」的 3D 模型？

在 Web 开发场景下，我们真正需要的不是一堆顶点数据，而是：

```text
- 可版本控制 —— Git 能 diff，PR 能 review
- 可编程 —— 能响应用户交互，能动态修改
- 可动画 —— 能定义枢轴点、旋转轴、运动逻辑
- 可复用 —— 能作为组件嵌入更大场景
```

这就是 img2threejs 的核心价值：**它不给你一个不透明的网格，而是给你一份可读、可编辑、可动画的 TypeScript 代码。**

## 第二章：img2threejs 是什么

一句话：**把一张图片变成一个程序化的 Three.js 模型——带类型定义、组件层级、动画就绪的 TypeScript 代码。**

### 两种生成路径

img2threejs 提供两条路径，解决不同场景需求：

| 路径 | 输入 | 输出 | 适用场景 |
|------|------|------|----------|
| **Procedural（程序化）** | 三视图（前/侧/顶） | TypeScript 代码 + JSON 规格 + GLB/glTF | 需要可编辑、可动画的代码模型 |
| **Native Mesh（原生网格）** | 一张普通图片 | 纹理化 GLB/glTF 资产 | 需要直接导入 3D 软件或引擎 |

### Procedural 模式的核心优势

为什么推荐 Procedural 模式？因为它把模型当作「软件」来管理：

```text
1. 代码即文档 —— 模型结构一目了然，组件命名清晰
2. Git 友好 —— 能看到每次修改改了哪个组件、哪个材质
3. 运行时可寻址 —— 门能开、轮能转、工具能插拔
4. 审查可追溯 —— 有照片 vs 渲染的对比图，记录每次决策
```

## 第三章：核心概念（由浅入深）

### 3.1 三视图板（Three-View Board）

Procedural 模式的核心输入是「三视图板」——一张包含物体前视图、侧视图、顶视图的参考图。

```text
为什么需要三视图？
- 单张图片无法揭示隐藏面（底面、背面、内部结构）
- 三视图提供完整的几何证据，让 AI 能推断比例和空间关系
- 类似工程制图的「正投影」，是精确重建的基础
```

你可以自己拍摄或绘制三视图，也可以用工具从普通照片生成。

### 3.2 质量合约（Quality Contract）

生成前，系统会输出一份 JSON 格式的「质量合约」，记录：

```json
{
  "subject": "cordless drill",
  "geometryEvidence": "three-view board",
  "requiredParts": ["chuck", "bit", "grip", "battery"],
  "next": "Generate Model"
}
```

这份合约是生成过程的「蓝图」，确保 AI 理解你要建什么、有哪些部件、用什么证据。

### 3.3 组件化建模（Component-Based Modeling）

img2threejs 生成的模型不是一整块网格，而是由多个命名组件构成的层级结构：

```text
Procedural 模型结构：
├── Root Group
│   ├── Chuck（卡盘）
│   │   ├── Jaw Assembly（夹爪组件）
│   │   └── Rotation Pivot（旋转枢轴）
│   ├── Bit（钻头）
│   ├── Grip（握把）
│   │   ├── Trigger（扳机）
│   │   └── Texture Map（纹理贴图）
│   └── Battery（电池）
│       ├── Release Button（释放按钮）
│       └── Contact Points（接触点）
```

每个组件都有：
- **命名**：语义化，可寻址
- **材质**：独立的材质定义
- **动画就绪**：枢轴点、旋转轴、运动范围

### 3.4 输出文件

Procedural 模式生成的文件：

```text
输出目录/
├── createModel.ts      主工厂函数（THREE.Group）
├── spec.json           模型规格（组件树、材质、规则）
├── model.glb           二进制 3D 资产
└── model.gltf          JSON 格式 3D 资产
```

## 第四章：实战上手（Practice）

### 第 1 步：准备参考图

最理想的是三视图板：

```text
┌─────────────────────────────────────┐
│           Front View                │
│                                     │
│  ┌─────────────────────────────┐    │
│  │                             │    │
│  │                             │    │
│  └─────────────────────────────┘    │
│                                     │
│  ┌─────────────┐ ┌─────────────┐    │
│  │ Side View   │ │ Top View    │    │
│  │             │ │             │    │
│  └─────────────┘ └─────────────┘    │
└─────────────────────────────────────┘
```

如果没有三视图，用一张清晰的正面照片也可以（Native Mesh 模式）。

### 第 2 步：访问在线转换器

打开 https://img2threejs.org/，你会看到：

```text
- Procedural 模式：上传三视图板，生成可编辑代码
- Native Mesh 模式：上传普通图片，生成纹理化模型
```

选择 Procedural 模式，上传你的三视图板。

### 第 3 步：分析与规划

系统会：

```text
1. 分析三视图，提取轮廓、比例、材质线索
2. 生成质量合约（quality-contract.json）
3. 列出识别到的组件（requiredParts）
4. 等待你确认后开始生成
```

检查合约内容，确保组件列表符合预期。如果遗漏了重要部件，可以补充参考图重新分析。

### 第 4 步：生成与预览

确认后，系统生成：

```text
- TypeScript 代码（createModel.ts）
- JSON 规格（spec.json）
- GLB/glTF 资产
```

在浏览器中预览渲染结果，与原始参考图对比。不满意？可以调整参数重新生成。

### 第 5 步：导出到项目

将生成的代码集成到你的 Three.js 项目：

```typescript
// 1. 复制 createModel.ts 到你的项目
// 2. 安装 three.js（如果还没装）
// npm install three
// npm install -D @types/three

// 3. 在你的代码中使用
import { createModel } from './createModel';

// 创建场景
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, window.innerWidth / window.innerHeight, 0.1, 1000);
const renderer = new THREE.WebGLRenderer();
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

// 加载生成的模型
const model = createModel();
scene.add(model);

// 动画循环
function animate() {
  requestAnimationFrame(animate);
  // 可以单独控制每个组件
  model.children[0].rotation.y += 0.01; // 旋转卡盘
  renderer.render(scene, camera);
}
animate();
```

## 第五章：深入原理（Advanced）

### 5.1 Procedural 生成流程

```text
输入：三视图板
  ↓
分析阶段：
  - 轮廓提取（Silhouette Detection）
  - 材质线索识别（Material Cues）
  - 附件点检测（Attachment Points）
  - 重复系统识别（Repeated Systems）
  ↓
规划阶段：
  - 组件分解（Component Decomposition）
  - 层级关系建立（Hierarchy Construction）
  - 动画约束定义（Animation Constraints）
  ↓
生成阶段：
  - TypeScript 代码生成
  - JSON 规格生成
  - GLB/glTF 导出
  ↓
审查阶段：
  - 渲染预览
  - 照片 vs 渲染对比
  - 质量评估
```

### 5.2 为什么不用传统的摄影测量（Photogrammetry）？

传统摄影测量（从多张照片重建 3D）的问题：

```text
1. 需要大量照片（通常 20-100 张）
2. 生成的是无语义的点云或网格
3. 难以编辑和动画
4. 对光照和纹理敏感
```

img2threejs 的优势：

```text
1. 只需 1-3 张参考图
2. 生成的是语义化的组件层级
3. 代码可编辑、可版本控制
4. 适合 Web 交互场景
```

### 5.3 与传统建模工具的对比

| 特性 | Blender | img2threejs |
|------|---------|-------------|
| 学习曲线 | 陡峭 | 几乎为零 |
| 输出格式 | 网格/纹理 | 代码 + 网格 |
| 可编辑性 | 需要软件 | 直接改代码 |
| 版本控制 | 困难 | Git 原生支持 |
| 动画 | 手动绑定 | 代码定义 |
| 适用场景 | 影视/游戏 | Web/交互 |

## 避坑清单

| 坑 | 正确做法 |
|----|---------|
| 用模糊或角度歪的照片 | 用清晰、正面、光线均匀的照片；Procedural 模式尽量用三视图 |
| 期望生成电影级角色 | 它擅长硬表面物体（产品、工具、设备），不适合有机形态 |
| 忽略质量合约 | 仔细检查 `requiredParts`，遗漏的部件不会被生成 |
| 直接用生成的 GLB 不看代码 | 优先使用 TypeScript 代码，GLB 只是备份或导入其他工具 |
| 期望 100% 还原 | 它是「重建」不是「复制」，遮挡面和内部结构需要额外参考 |
| 忘记动画就绪 | 生成的组件已有枢轴点，但复杂动画仍需手动调整 |
| 不测试就上线 | 在浏览器中预览，检查比例、材质、交互是否符合预期 |
| 混淆两种模式 | Procedural 用于可编辑代码，Native Mesh 用于纹理化资产 |

## 小结

一句话总结 img2threejs 的定位：**它把 3D 建模从「手工雕刻顶点」变成了「AI 分析 + 代码生成 + 人工审查」的工程化流程。**

```text
Procedural  → 可编辑的 Three.js 代码
Native Mesh → 纹理化的 GLB/glTF 资产
共同目标    → 降低 3D 内容创建门槛
```

如果你是 Web 开发者，想在项目中加入 3D 元素但不想学 Blender；如果你是产品经理，想快速验证 3D 交互原型；如果你是设计师，想把概念图快速变成可交互的模型——img2threejs 值得一试。
