## 引言：AI 不缺聪明，缺的是「你们的规矩」

把一段需求丢给 AI 编程助手，它能在几十秒内写出看起来漂亮的代码。但很快你会遇到这些问题：

- 它用 `npm test` 跑测试，而你们项目实际用 `make check`；
- 它「顺手重构」了 `dist/`，那是构建产物，改了等于埋雷；
- 它写的代码能跑，但和团队风格格格不入，评审时全要重写；
- 换一个会话、换一个模型，同样的需求又得到完全不同的答案。

问题不在模型不够强，而在于**项目的隐性知识没有被写出来**。哪些命令能跑、哪些目录是禁区、提交要什么格式——这些老员工烂熟于心的规则，AI 只能靠猜。

![为什么需要 AGENTS.md](/images/agents-why.png)

**AGENTS.md** 就是解决这件事的：一个放在项目根目录的纯文本约定文件，AI 开工前会读它。它把「只有老员工知道」的规矩，变成随代码一起版本化的显性说明书。

这篇文章按四层走：先讲清它是什么，再写出最小可用版本，然后用三个**实测可运行**的示例深入，最后给出落地闭环和避坑清单。

## 第一层：AGENTS.md 到底是什么

一句话：**它是写给 AI 看的 README**。

两者的区别很关键：

| | README.md | AGENTS.md |
|---|---|---|
| 读者 | 人 | AI 编程代理 |
| 关注点 | 项目介绍、安装教程、功能展示 | 构建命令、目录约定、代码风格、禁止事项 |
| 语气 | 吸引人、讲背景 | 短、具体、可执行 |
| 典型内容 | 「这是一个现代化的博客系统」 | 「构建用 `npm run build`，不要改 `dist/`」 |

目前主流 AI 编码工具（如 OpenAI Codex、Claude Code、Cursor 等）都支持在项目根目录读取 `AGENTS.md`，作为会话级别的「常驻指令」。它不需要特殊格式，就是普通的 Markdown。

**核心原则**：一条「跑 `npm test`」胜过三段「请保持代码质量」。AI 不需要激励，需要指令。

## 第二层：最小可用版本，十分钟写完

你不需要一开始写出完美文档。下面这个骨架覆盖 80% 的场景，十分钟内就能写完：

```markdown
# AGENTS.md

## 构建与测试
- 构建：`python3 -m compileall -q src`
- 测试：`python3 -m unittest discover -s tests -v`

## 目录约定
- `src/`：业务代码，可自由修改
- `dist/`：构建产物，禁止手动修改

## 代码风格
- 所有函数必须有类型注解
- 禁止在业务代码里 print 调试，用 logging

## 提交规范
- 使用 Conventional Commits，如 `feat:`、`fix:`

## 禁止事项
- 不要提交 `.env`
- 不要修改第三方依赖目录
```

![AGENTS.md 的结构](/images/agents-structure.png)

写的时候记住三条：

1. **命令要能直接复制粘贴**，带上参数和路径，不要写「运行测试即可」。
2. **规则要可判定**，不要写「代码要优雅」，要写「函数超过 50 行必须拆」。
3. **禁止事项要显式**，AI 默认不会猜想哪些目录不能碰，必须明说。

## 第三层：三个实测示例

下面三个示例我都实际运行过，输出真实可复现。你可以把它们直接复制到自己的项目里改。

### 示例一：先看看「没有约定」会怎样

这个脚本模拟 AI 接手一个只有简单 README 的项目时，能推断出多少关键信息：

```python
# check_readme.py
from pathlib import Path

readme = Path("test_bad.md").read_text(encoding="utf-8")
checks = {
    "是否有构建命令": "npm run build" in readme or "make" in readme,
    "是否有测试命令": "pytest" in readme or "npm test" in readme,
    "是否有目录说明": "src/" in readme or "目录" in readme,
}
for k, v in checks.items():
    print(f"{k}: {'✅' if v else '❌'}")
```

运行输出：

```text
是否有构建命令: ❌
是否有测试命令: ❌
是否有目录说明: ❌
```

一份只有「这是一个项目」的文档，AI 需要的三类关键信息一个都拿不到。这不是模型笨，是信息根本不在那里。

### 示例二：有约定之后，命令直接可用

我把上面那份最小版 AGENTS.md 放进一个真实的 Python 小项目，然后严格按里面的命令执行：

```text
$ python3 -m compileall -q src      # 构建
build ok

$ python3 -m unittest discover -s tests -v
test_add (test_calc.TestAdd.test_add) ... ok
----------------------------------------------------------------------
Ran 1 test in 0.000s
OK
```

关键在于**确定性**：AI 不需要去翻 `package.json`、不需要猜测试框架、不需要问你「用哪个命令」。文档里写了什么，它就执行什么，结果可预期。

### 示例三：用脚本自检「文档写全了没」

文档写完后，怎么确认没有漏项？用一段正则自检脚本，把约定变成可验证的检查：

```python
# audit_agents.py
import re
from pathlib import Path

text = Path("AGENTS.md").read_text(encoding="utf-8")
required = {
    "构建命令": r"构建|build",
    "测试命令": r"测试|test",
    "代码风格": r"约定|风格|style",
    "提交规范": r"提交|commit",
}
print("AGENTS.md 自检报告：")
for name, pat in required.items():
    ok = bool(re.search(pat, text, re.I))
    print(f"  {'✅' if ok else '❌'} {name}")
```

第一次运行（此时还没写提交规范）：

```text
AGENTS.md 自检报告：
  ✅ 构建命令
  ✅ 测试命令
  ✅ 代码风格
  ❌ 提交规范
```

补上一行 `- 使用 Conventional Commits，如 feat:、fix:` 后再跑：

```text
  ✅ 构建命令
  ✅ 测试命令
  ✅ 代码风格
  ✅ 提交规范
```

这个脚本可以挂到 CI 或 pre-commit 里。它拦住的不是「写得不好的文档」，而是「空壳文档」——那种只有标题没有任何实质约定的摆设。

## 第四层：让它真正生效的四个习惯

写完文件只是开始。下面四个习惯决定它是不是「活文档」：

1. **放在项目根目录，和代码一起提交**。不要只存在个人笔记里，否则换人、换模型就失效。
2. **新会话第一句话就让 AI 先读它**。例如：「先读 AGENTS.md，再开始工作」。常驻指令和一次性指令的优先级不同，显式点名最保险。
3. **AI 理解错一次，就补一条规则**。这是文档进化的最好时机——错误是真实的需求信号。
4. **定期精简**。删掉过时的命令、合并重复的规则。一份 60 行、条条有用的文档，胜过 300 行的流水账。

## 避坑清单

- ❌ **写成哲学宣言**：「追求卓越、保持简洁」这类话对 AI 毫无信息量。改成可判定的规则。
- ❌ **把 README 复制进来**：AI 不需要产品介绍，它需要操作手册。
- ❌ **命令写死在本地环境**：`cd /Users/yourname/project` 这种绝对路径换个机器就废，用相对路径。
- ❌ **只写「做什么」不写「不做什么」**：`dist/`、`node_modules/`、`.env` 这些禁区必须显式声明。
- ❌ **过长过细**：把代码库全部铺开复述一遍，会稀释关键规则，还可能挤占上下文。抓高频场景即可。
- ❌ **写完就不管**：依赖升级、命令变更后要同步更新，否则 AI 会「认真地执行错误的指令」。
- ❌ **以为它能替代代码审查**：AGENTS.md 降低出错率，但不保证正确。该 review 的还是要 review。

## 小结

AGENTS.md 的本质不是「提示词技巧」，而是**把团队隐性知识资产化**。它让 AI 从「聪明但不了解你项目的实习生」，变成「读过入职手册的队友」。

从今天开始，花十分钟写一份最小版本，然后在每次协作中慢慢喂它——这是投入产出比极高的工程习惯。
