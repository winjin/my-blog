大多数人用 Git 只停留在 `add`、`commit`、`push`、`pull`，但这些只是 Git 的冰山一角。Git 真正的威力在于它对**历史**的掌控：你可以改写、合并、搬运、恢复提交，让项目历史保持干净整洁。

这篇文章用大量可运行的命令，把 Git 的进阶能力一次讲透。

## 第一章：工作区、暂存区、仓库

先建立正确的心理模型：

```text
工作区（Working Directory）
  │  git add
  ▼
暂存区（Index / Staging）
  │  git commit
  ▼
本地仓库（Local Repo）  ── git push ──►  远程仓库（Remote）
```

```
工作区 = 你看到的文件
暂存区 = 准备提交的快照（类似"拍照前的摆拍"）
仓库   = 已保存的历史快照
```

## 第二章：拯救误操作——reflog

`git reflog`（reference log）会记录 HEAD 的**每一次移动**，包括 reset、rebase、checkout 等操作。它是 Git 的「后悔药」：

```bash
# 查看 HEAD 的移动历史
git reflog

# 输出类似：
# 3a1b2c3 HEAD@{0}: commit: 修复登录 bug
# 8d4e5f6 HEAD@{1}: reset: moving to HEAD~1
# 7f8g9h0 HEAD@{2}: commit: 添加搜索功能
```

**常见误操作找回：**

```bash
# 误删分支，用 reflog 找回 commit，再重建分支
git reflog
git branch recovered-branch 8d4e5f6

# 误 reset 丢掉提交，回到 reset 前的状态
git reset --hard HEAD@{1}

# 删掉了未推送的分支
git branch backup 7f8g9h0
```

**核心心法：** 只要 commit 曾经存在过，reflog 就能帮你找回。Git 一般不会立即 GC（垃圾回收），你有约 90 天（默认 `gc.reflogExpire`）的找回窗口。

## 第三章：stash——临时保存工作区

写到一半要切换分支？先 stash 起来：

```bash
# 保存当前未提交的改动
git stash

# 查看 stash 列表
git stash list

# 恢复最近一次 stash 并删除记录
git stash pop

# 恢复但不删除记录
git stash apply

# 带备注保存（推荐）
git stash push -m "WIP: 修复登录页样式"
git stash push -m "搜索功能写到一半"

# 恢复指定 stash
git stash apply stash@{1}

# 查看某个 stash 的改动内容
git stash show -p stash@{0}

# 删除指定 stash
git stash drop stash@{0}

# 清空全部
git stash clear
```

**经典场景：**

```bash
# 1. 功能写一半，需要切到其他分支修 bug
git stash push -m "feature 进行中"
git checkout fix-branch
# 修完 bug 回来
git checkout feature-branch
git stash pop

# 2. 只暂存部分文件
git stash push -m "只暂存这两个文件" src/App.tsx src/utils.ts
```

## 第四章：cherry-pick——精准搬运提交

`cherry-pick` 把某个提交复制到当前分支，像摘樱桃一样精准：

```bash
# 把 commit A 应用到当前分支（生成一个全新的 commit）
git cherry-pick A

# 连续搬运多个提交
git cherry-pick A B C

# 从一个分支范围搬运
git cherry-pick feature-branch~2..feature-branch

# 只应用改动但不自动提交（方便手动调整）
git cherry-pick -n A
```

**经典场景：**

```text
main分支：        M1 ─ M2
                     \
feature分支：        F1 ─ F2 ─ F3

你在 feature 上修好了 F2 的 bug，
但还没到合并的时候，想先让 main 也有这个修复：

git checkout main
git cherry-pick F2
```

**⚠️ 注意：** cherry-pick 会生成新的 commit（哈希值不同），所以它适合「把一个修复搬到多个分支」，但不要用它在多个地方重复提交同一功能——那会造成重复代码。

## 第五章：rebase——整理提交历史

`rebase` 是把提交「重新安放」到另一个基点：

```bash
# 把当前分支的提交，重新基于 origin/main
git rebase origin/main

# 交互式 rebase：重排、合并、改提交信息
git rebase -i HEAD~3

# 输出编辑器：
# pick 3a1b2c3 修复登录
# pick 8d4e5f6 添加搜索
# pick 7f8g9h0 修复搜索的 bug

# 改成：
# pick 3a1b2c3 修复登录
# squash 8d4e5f6 添加搜索      ← 合并进上一个
# reword 7f8g9h0 完成搜索功能   ← 改提交信息
```

**rebase 交互模式常用动词：**

| 动词 | 简写 | 作用 |
|------|------|------|
| `pick` | `p` | 保留该提交 |
| `reword` | `r` | 修改提交信息 |
| `edit` | `e` | 停在该提交，允许修改内容 |
| `squash` | `s` | 合并到上一个提交 |
| `fixup` | `f` | 合并到上一个提交（丢弃信息） |
| `drop` | `d` | 删除该提交 |

**经典场景——把一堆小提交整理成一个：**

```bash
# 你做了 5 个小提交，想让历史看起来像一个大功能
git rebase -i HEAD~5
# 保留第一个 pick，其余 4 个改成 squash
```

**rebase vs merge：**

```text
merge：
  main:   M1 ──── M2
                ╱
  feature:  F1 ─ F2
  历史有分叉，保留真实合并记录（适合团队主干）

rebase：
  main:   M1 ── F1' ─ F2' ── M2
  feature:  F1 ─ F2  （被重放）
  历史是一条直线（适合个人分支整理）
```

## 第六章：reset vs revert——撤销的艺术

```bash
# ---- reset：移动 HEAD，改写历史（本地用）----
git reset --soft HEAD~1     # 撤销提交，改动保留在暂存区
git reset --mixed HEAD~1    # 撤销提交，改动保留在工作区（默认）
git reset --hard HEAD~1     # 撤销提交，改动全部丢弃（⚠️危险）
git reset --hard origin/main # 回到远程状态

# ---- revert：生成反向提交，不改写历史（远程用）----
git revert <commit>         # 新增一个提交，把改动反向撤销
```

**怎么选：**

| 场景 | 命令 | 原因 |
|------|------|------|
| 提交错了，还没 push | `reset --soft` | 本地历史，改写无副作用 |
| 已经 push，要撤销 | `revert` | 不改写远程历史，安全 |
| 想彻底丢弃工作区改动 | `checkout -- <file>` | 一键还原文件 |
| 想撤销单个文件到某版本 | `git restore --source=A -- file` | 精准还原 |

**已推送的错误提交，用 revert：**

```bash
git revert 8d4e5f6
# 会生成一个 "Revert 8d4e5f6" 的新提交
# 团队其他人 pull 就能安全地撤销
```

## 第七章：submodule 与 subtree——子项目管理

项目依赖另一个项目？有几种方案：

```bash
# ---- submodule：把远程仓库作为子目录 ----
git submodule add https://github.com/foo/shared-lib.git libs/shared
git submodule update --init --recursive  # clone 后初始化
git submodule update --remote            # 更新到最新

# ---- subtree：把子项目代码直接并入 ----
git subtree add --prefix=libs/shared https://github.com/foo/shared-lib.git main
git subtree pull --prefix=libs/shared <remote> main
```

**submodule vs subtree：**

| 对比 | submodule | subtree |
|------|-----------|---------|
| 子项目独立性 | 强（独立仓库） | 弱（并入本仓库） |
| 克隆复杂度 | 需 `--recursive` | 一条命令完成 |
| 团队心智负担 | 高（易忘记 init） | 低 |
| 适用场景 | 明确版本锁定 | 简单集成第三方代码 |

> 💡 多数团队的新项目更推荐 subtree 或直接 npm/pip 依赖，submodule 的坑比较多（切换分支后子模块状态容易混乱）。

## 第八章：Git 配置技巧

```bash
# 全局用户信息
git config --global user.name "你的名字"
git config --global user.email "you@example.com"

# 常用别名（大幅提升效率）
git config --global alias.st "status -sb"
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.lg "log --oneline --graph --all"
git config --global alias.unstage "reset HEAD --"

# 颜色高亮
git config --global color.ui auto

# 记住凭证（macOS/Windows 安全存储）
git config --global credential.helper osxkeychain

# 自定义 log 视图
git config --global alias.tree "log --graph --pretty=format:'%h %s %d'"
```

## 第九章：分支管理最佳实践

```bash
# 建立新分支
git checkout -b feature/login-page main

# 同步远程分支列表
git fetch --all --prune

# 删除已合并的分支（本地 + 远程）
git branch -d feature/old
git push origin --delete feature/old

# 查看每个分支领先/落后多少
git branch -vv

# 清理已合并的本地分支
git branch --merged main | grep -v main | xargs git branch -d
```

## 避坑清单

| 坑 | 正确做法 |
|----|---------|
| 对已 push 的分支用 `reset --hard` | 已推送的提交用 `revert` 撤销，别改写远程历史 |
| 多人共用分支上 rebase | 只 rebase **自己没推过**的提交；已推过的会害队友 |
| 直接 `stash` 不写备注 | `stash push -m "说明"`，不然 stash@{2} 没人记得是啥 |
| 忘 stash 就切换分支 | 有未提交改动时先 `stash`，否则 checkout 可能报错或带过去 |
| `rebase -i` 合并后 push 失败 | 本地 rebase 完 push 冲突，先 `git pull --rebase` |
| 找不到丢掉的提交 | 先查 `git reflog`，别急着重建分支 |
| 交互式 rebase 中断了 | 解决冲突后 `git rebase --continue`；想放弃 `git rebase --abort` |
| 把敏感信息提交了 | 用 `filter-repo` 或 BFG 重写历史（`filter-branch` 已过时），并立即轮换密钥 |
| 死记命令 | 记住概念（历史指针怎么移动），命令自然能推导出来 |
| 忽略 `.gitignore` | 先把 `node_modules`、`.env`、密钥文件写进 `.gitignore` 再首次 commit |

## 小结

```text
reflog   = 后悔药（找回一切）
stash    = 移动工作台（临时存改动）
cherry-pick = 搬运工（复制提交）
rebase   = 整理工（历史变直线）
reset    = 本地撤销（改写历史）
revert   = 远程撤销（安全回退）
```

Git 的本质不是「记录文件」，而是**记录历史快照之间的指针关系**。理解这一点，你就不会怕任何 Git 操作——因为几乎所有误操作都能用 reflog 找回来。

建议你现在就动手：造一个测试仓库，把 rebase -i、stash、cherry-pick、reflog 都演练一遍。**Git 是唯一一个「越敢折腾、越不丢数据」的工具。**
